Test Techniques Cheat Sheet

Start with the question you need to answer

Techniques are ways to choose and organize tests, not recipes that guarantee defect discovery. Begin by naming the behavior, available test basis, and risk. Are you checking a numeric range, combinations of business rules, event sequences, internal decisions, or a poorly understood feature? Then choose a method that makes the important coverage visible. You can combine methods when one view is not enough.

Black-box quick reference

  • Equivalence partitioning: divide values into groups expected to behave similarly and choose representative values. Good for broad input spaces and validation rules.
  • Boundary value analysis: test near the edges of ordered partitions, where off-by-one errors are common. Include values immediately below, at, and above a threshold when appropriate.
  • Decision table testing: list condition combinations and their expected actions. Useful when multiple rules interact, such as eligibility, payment, and shipping.
  • State transition testing: model states, events, and resulting states. Check valid transitions, important sequences, and rejected events.
  • Use-case testing: follow user goals and alternative paths through a workflow, including failures and recovery.

White-box and experience-based methods

  • Statement coverage: check which executable statements have run. It does not guarantee every decision outcome was exercised.
  • Branch coverage: exercise each decision outcome, such as true and false. It often requires more tests than statement coverage.
  • Error guessing: use knowledge of likely failure modes to try risky inputs and sequences.
  • Exploratory testing: learn, design, and execute in parallel under a focused charter. Capture findings and useful test ideas.
  • Checklist-based testing: use a concise, maintained list of risks or conditions to make recurring checks consistent.

Worked example: password policy

Suppose a password must contain 10 to 64 characters and must not be a commonly blocked password. Equivalence partitions include too short, valid length, too long, and blocked values. Boundary analysis suggests lengths 9, 10, 64, and 65. The blocked-password rule adds a separate dimension: try a blocked value of valid length and an allowed value of valid length. If the account has states such as active, locked, and reset-pending, state transition tests can examine password changes and sign-in attempts in those states. This combination is clearer than selecting many arbitrary strings.

Choosing the technique

For a range or limit, start with partitions and boundaries. For several boolean or categorical rules, build a decision table and reduce combinations only when justified. For workflows, map states and user goals. For code-level confidence, inspect statement and branch coverage alongside requirements-based tests. For unfamiliar interfaces, define an exploratory charter such as “investigate recovery after interrupted checkout,” then record the environment and observations.

Every method has blind spots. A complete table can still encode a wrong business rule. Full branch coverage can miss omitted requirements. A checklist can become stale. Use independent review and real user context to challenge the model behind your tests.

Key terms

  • Partition: a group of inputs expected to be treated alike.
  • Boundary: an edge between input groups or rule outcomes.
  • Condition: a rule or factor that influences an outcome.
  • State: a defined situation that affects how events are handled.
  • Coverage item: an element used to assess how much testing was done.
  • Charter: a goal or boundary that guides an exploratory session.

Before calling a technique complete, state what it covered and what remains. Coverage numbers are meaningful only when the underlying items and exclusions are understood.

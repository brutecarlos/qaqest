Static Testing

Inspect before execution

Static testing evaluates a work product without running the software. It can be applied to requirements, architecture diagrams, test cases, source code, user help, contracts, or operational procedures. A person may inspect a document manually, or a static analysis tool may detect patterns in code. The key distinction is that the product under examination is not being executed.

Static work is valuable when behavior is expensive to run, when defects would be costly to find late, or when the work product itself needs to be clear and consistent. It can reveal ambiguity, omissions, contradictions, duplicated logic, coding-standard violations, or suspicious constructs. It cannot prove how the running system behaves under real conditions, so it complements rather than replaces dynamic testing.

Reviews as structured collaboration

A review is an examination involving people who provide feedback on a work product. Informal reviews can be a quick peer read. More structured forms define roles and steps: planning, individual preparation, a discussion or defect analysis, correction, and follow-up. Roles may include an author, moderator, reviewer, and recorder, though small reviews can combine responsibilities. A moderator helps the review stay constructive and focused; a recorder captures issues for follow-up.

Review objectives can include finding defects, improving shared understanding, transferring knowledge, and checking compliance. The objective determines who should attend and what preparation is useful. Reviewers should examine the material before the meeting and record questions or suspected issues. A meeting is not a substitute for preparation, nor should it become a session for rewriting the author's work line by line.

Review findings with care

Useful feedback points to a specific location, describes the concern, and explains its consequence. Separate a potential defect from a style preference. Phrase issues neutrally: “The retry rule does not specify what happens after the third attempt” is more actionable than “This is confusing.” The author is responsible for evaluating and addressing findings; the review group helps surface them.

Worked example: review an acceptance rule

A requirement says, “The account locks after repeated failed sign-in attempts.” Reviewers can ask: How many attempts? Over what period? Does a successful sign-in reset the count? What does the user see? Is the lock temporary, and how is recovery handled? These questions expose missing decision rules before code is written. Later, the answers can become test conditions and concrete cases. A review has thus improved both the requirement and the future test basis.

Static analysis tools

Static analysis tools examine artifacts using automated rules. A code linter may flag style inconsistencies; a type checker may find incompatible values; a security analyzer may identify risky patterns. Configure rules thoughtfully: a large flood of low-value warnings can train people to ignore findings. Review false positives, make priorities explicit, and track whether the tool catches issues that matter. Tool output is evidence for investigation, not an infallible verdict.

Key terms

  • Static testing: evaluation without executing the work product.
  • Review: human examination of a work product.
  • Inspection: a formal review with defined roles and process.
  • Static analysis: automated examination of artifacts, often source code.
  • Defect: a flaw that can make the work product incorrect or unsuitable.

Static and dynamic findings differ in form. A requirement review may identify an undefined boundary; a running test may reveal a failure at that boundary. Combining both approaches improves early feedback and execution-based confidence.

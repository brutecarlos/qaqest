Test Analysis & Design

From test basis to test cases

Test analysis identifies what can be tested and the conditions worth checking. Test design turns those conditions into cases, data, and expected results. A test technique provides a systematic way to select or derive checks. The best technique depends on the available information, risk, time, and the behavior under study; techniques can be combined rather than treated as competing choices.

Black-box techniques

Black-box techniques derive tests from externally visible behavior or specified rules, without relying on internal code structure. Equivalence partitioning groups inputs expected to behave alike and samples from each group. Boundary value analysis focuses on edges, where mistakes are common. Decision tables expose combinations of conditions and resulting actions. State transition testing checks how events move a system between states, including invalid transitions.

Worked example: delivery fee. A service charges no fee for baskets of $50 or more; otherwise it charges $5. Partitions are below $50 and at least $50. Boundary checks at $49.99, $50.00, and $50.01 are more informative than three arbitrary amounts in the middle of the same group. For a rule with membership status and basket total, a decision table can ensure every meaningful combination and fee outcome is represented.

White-box techniques

White-box methods use internal structure, such as statements, branches, or control flow, to guide tests. Statement coverage asks whether each executable statement ran; branch coverage asks whether each decision outcome was exercised. A test suite may achieve full statement coverage while never taking the false outcome of a conditional, which is why branch coverage often reveals additional gaps. Coverage is a measure of exercised structure, not proof that the software is correct or that requirements are complete.

Worked example: eligibility logic. Code grants a discount when a customer is active and the order is above a threshold. Test an eligible customer with a large order and an inactive customer with a large order to exercise the true and false outcomes of the active check. Then consider a small order for an active customer to exercise the other decision. Review the exact control flow to avoid assuming that executing a line means all its logical outcomes were tested.

Experience-based techniques

Experience-based approaches use a tester's knowledge, intuition, and past observations. Error guessing turns likely mistakes into focused checks: empty values, stale sessions, repeated clicks, unusual Unicode, or a network interruption. Exploratory testing combines learning, test design, and execution as the tester investigates an area. A charter gives the exploration direction while leaving room to follow evidence. Checklist-based testing uses remembered risks or standards to make repeated work more consistent.

Experience is not a substitute for a clear test basis. Record the charter, environment, observations, and issues so that results are explainable and useful to others. Combine exploratory work with planned coverage: systematic cases help protect known rules, while exploration can reveal behavior nobody thought to specify.

Choose and combine methods

Use partitions and boundaries for numeric ranges, tables for interacting rules, and state models for event-driven behavior. Use structural coverage when internal logic is important and code is available. Use exploration when the product is unfamiliar or the documented model is incomplete. Risk should affect depth: a financial calculation deserves more combinations and independent review than a cosmetic label.

Key terms

  • Test condition: an aspect of a test basis selected for testing.
  • Coverage item: an element a technique aims to exercise.
  • Coverage: the proportion of selected items exercised by tests.
  • Test oracle: a source used to decide whether an observed result is correct.
  • Exploratory testing: concurrent learning, design, and execution guided by a charter.

Before execution, check that each case has an observable expected outcome. A technique can help choose inputs, but it does not automatically supply a trustworthy oracle.
